## Delivered access behavior

- Additive schema version 9: named roles, explicit capability lists, revisions, role assignment on users/invitations and access-change audit. Existing users and invitation keys map to Admin or Operator. Historical attribution is not rewritten.
- Admin retains all 56 capabilities; Operator retains the existing 17 default capabilities. Default roles cannot be edited; administrators copy either default or start with an empty role. One named role is assigned per person.
- Settings → Roles and Permissions groups capabilities, states prerequisites, previews navigation/settings and shows the number of affected people. Assignment and editing are audited. Invite registration uses the stored role and cannot accept a caller-supplied upgrade.
- Role management/access grants require a full administrator. Assignment, user suspension and editing an in-use custom role protect the last active full administrator. Role revisions protect concurrent edits.
- Current user/session/status/role is reread at service entry. Navigation, server-rendered controls, browser controls, default-deny route policy and mutating services use the central catalog. Team viewing, assignment, execution, review, count viewing/performing/recount/approval/conditions, catalog changes, hardware viewing/testing/mapping/flashing and backup actions are distinct.
- Operators with only added hardware viewing can open Settings → Hardware health/mappings, with no configuration forms, flash wizard, tests, people, roles or backup controls. Direct denied requests are rejected before mutation.
- Work scope includes own assignments and permitted history; Team and review scope require their corresponding rights. Execution remains exclusively the current assignee even for Admin. Read pages do not grant command permission. Restricted Work-only roles receive contextual products/locations rather than unrestricted warehouse contents.
- Same-session role changes take effect on the next server request. Saved earlier physical actuals, corrections and count observations retain their original person/device/request identities; revocation routes physical evidence to review/recheck without posting stock. Replays remain exactly-once. Inactive/revoked sessions cannot deliver under another account. Device help remains reachable for saved updates.

## Work amendment

The authoritative amendment is `LightGuide-work-refinement-requirements.md` beside the integrated UX plan in the coordinator's document folder. Its table/list requirements supersede earlier task-card proposals; section 8 supersedes earlier review vocabulary.

- Primary Work and sign-in land on My work for Admin and Operator. Pick/Put remain prominent. Team/review/history links are explicit.
- My work, Team work and history use semantic table rows with task/product, requested/remaining units, status/deadline, recorded progress, Assigned to, Performed by, Entered by, assignment time and actions. Names use usernames where disambiguation is needed. Narrow screens keep controlled table scrolling and keyboard/touch access.
- Untouched assigned decline returns one request to Needs assignment, with original deadline/history and no stock-review case. Eligible operators are searchable inside the row; Save changes ownership under the existing assignment generation. Task details use the same reassignment command.
- Untouched self-created cancellation retains cancelled history and safely releases its holds, without a review or reassignment queue item. Known partial actuals remain settled. Working/uncertain/conflicting physical evidence continues to require review. Local unreceived physical evidence blocks contradictory cancel/return actions.
- Inactivity no longer creates uncertainty for untouched modern reservations or unaccepted assignments. Active instructions still become review cases. Legacy instructions retain conservative timeout treatment because the older workflow may already have issued guidance. An old automatic inactivity case can be retired during cancellation/return only when persisted modern instructions show no start/device/turn/arrival/explicit uncertainty and all pending evidence is the exact old automatic unknown-quantity case; original entries/events remain. Explicit uncertainty is not cleared.
- SQL selection returns at most 100 task rows per page. Active, overdue, needs-assignment and history filters query the entire authorized set, with full-set counts. More than 100 older active tasks cannot be hidden by newer completed tasks. Explicit task links retrieve the authorized old task independently of the list page. Live responses may also carry at most 100 already-visible task updates so completion can be shown while an editor stays open.
- Visible pages poll every five seconds with backoff to sixty seconds when disconnected. Monitoring never touches task deadlines, generations or activity timestamps. During editing, rows are patched without replacing the edited form; its exact draft/generation/selection/focus stays in place, unrelated/new rows update, and table/page scroll is preserved. Stale saves are checked by the server. Open disclosures and persisted drafts survive ordinary rendering. Editing may temporarily retain a row that moved outside the current filter; pagination/filter navigation restores canonical ordering.
- Needs review supports combined searchable Assigned to / Performed by filters, grouping, unknown/inactive people, distinct usernames, total and filtered counts, clear reasons and next actions. Each case still requires its own quantity/evidence/permission/revision; no bulk inference of unknown quantities.
- Count cases show real recorded/count quantities, movement direction/quantity, time and known people. A searchable count selector replaces raw ID entry. “Already included in this count”, “This was a separate pick/put” and “I’m not sure — keep pending” retain the original exact-once checks. Duplicate matching uses “Has this pick/put already been saved?”, human entry details, View saved entry and Use this saved entry, with no second stock change. Exceptional controls remain contextual or in More options.
- Work uses Saved updates, Send saved updates, Download saved updates and Entered by. The mixed queue names the actual action and distinguishes no confirmed receipt, received-but-awaiting-check, rejected evidence and failed commands. Internal report IDs/storage and analytical Reports are unchanged. Internal IDs are absent from ordinary queue copy.

## Firmware decision and physical validation boundary

Use bundled offline compilation, not one fixed prebuilt binary. Module count, controller name and address remain compile-time settings. The protocol remains `simple-matrix-v12-rs485-addressed`; board target is `esp32:esp32:esp32`.

Pinned CLI/core/library preparation and the host adapter were exercised with an actual official Arduino toolchain staged only in a temporary folder. Two real compile runs succeeded with network access blocked: 1 module (305,409 program bytes, 21,168 global data bytes) and 64 modules (305,661 program bytes, 28,472 global data bytes), with different names/addresses. Compilation exposed and fixed the prior missing `-MMD -c` flags. Repeated compilation through the final subprocess adapter also passed. See [compile log](phase-3-evidence/offline-compile.txt) and [versions/hashes](phase-3-evidence/firmware-proof.json). Simulator results are explicitly separate and do not claim real compilation/flashing.

**Pending Phase 4 hardware gates:** assemble and test the Linux ARM64 bundle on the actual supported Pi image; verify clean-install offline compile, serial permissions, USB/RS485 identity and aliases, bus framing/timing, controller discovery/health, 1–64-module output mapping, actual flash and reconnect, disconnect/interruption recovery, busy-work exclusion and replacement safeguards. No Pi or ESP32 was attached here. macOS compiler evidence is not Pi-host certification; no Mac installer or physical-flash signoff is delivered.
